## 2. Prepare certificates and candidate configuration — no activation

Validate the reviewed delivered files before installing anything:

```sh

sudo openssl verify -no-CApath -no-CAstore -CAfile "$REVIEWED_CERT_DIR/ca.pem" \
  -purpose sslserver -auth_level 2 -verify_hostname mysql "$REVIEWED_CERT_DIR/server-cert.pem"
```

Verify the exact DNS SAN and key matching without displaying key material:

```sh
sudo openssl x509 -in "$REVIEWED_CERT_DIR/server-cert.pem" -noout -ext subjectAltName
sudo sh -eu -c '
  umask 077
  work=$(mktemp -d /run/goevent-cert-check.XXXXXX)
  cleanup() { rm -f "$work/cert.pub" "$work/key.pub"; rmdir "$work"; }
  trap cleanup EXIT
  openssl x509 -in "$1/server-cert.pem" -pubkey -noout > "$work/cert.pub"
  openssl pkey -in "$1/server-key.pem" -passin pass: -pubout > "$work/key.pub"
  cmp -s "$work/cert.pub" "$work/key.pub"
' sh "$REVIEWED_CERT_DIR"
```

## 4. Migration identity, then runtime privilege reduction

Follow the [protected password-file/Key Vault/SQL generation procedure](APPLICATION-BOOTSTRAP.md#mysql-server-tls-and-account-review-separate-owner-change).
Use a new distinct password, store it in Key Vault, pin its version, and create
`goevent_migration` with an explicitly approved host selector and REQUIRE SSL.
For `%` (only if separately approved for the private network), the reviewed grant is:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
 ON `goevent_db`.* TO 'goevent_migration'@'%';
```

No global privilege, GRANT OPTION or DROP privilege is needed by current V1–V5.
Do not mask an unexpectedly existing account with IF NOT EXISTS. Do not print or
pass its password as a command argument; execute its generated private SQL through
`mysql_root < /protected/path/migration-account.sql`, after SQL logging/history
handling is reviewed. Do not rotate app/root credentials or modify their bootstrap.

Independently verify migration authentication before reducing app privileges:

```sh
sudo docker exec -i --user 0 "$MYSQL_CONTAINER" mysql --defaults-extra-file="$MIGRATION_CNF" \
  --protocol=TCP --host=mysql --ssl-mode=VERIFY_IDENTITY \
  --ssl-ca=/etc/goevent-mysql-tls/ca.pem --database=goevent_db --batch \
  --execute="SELECT CURRENT_USER(); SHOW SESSION STATUS LIKE 'Ssl_cipher'; SHOW GRANTS;"
```

Require CURRENT_USER `goevent_migration@<approved-host>`, a non-empty cipher
and exactly the approved grants. Prove V1–V5 compatibility on an **isolated restored
clone named goevent_db**, with the migration account and runtime DML account split.
Keep the real empty database empty: no probe tables, Flyway baseline or actual
application migration in this maintenance step. Zero-table metadata checks alone
cannot establish DML/Flyway compatibility.

**Only after that separate credential/compatibility acceptance**, with all app
and backup/other consumers of goevent_app quiesced or verified compatible:

```sql
REVOKE ALL PRIVILEGES ON `goevent_db`.* FROM 'goevent_app'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON `goevent_db`.* TO 'goevent_app'@'%';
ALTER USER 'goevent_app'@'%' REQUIRE SSL;
SHOW GRANTS FOR 'goevent_app'@'%';
```

Account statements autocommit: there is a temporary privilege gap, not an atomic
transaction. Root recovery must remain available. This schema-only REVOKE assumes
inspection found no GRANT OPTION, global/role/object grants; otherwise stop for a
separate plan. Verify on **new** app/migration connections with the exact TCP commands above;
inspect schema privileges as in the baseline query. Expect app privileges exactly
DELETE/INSERT/SELECT/UPDATE, IS_GRANTABLE=NO and ssl_type=ANY. Confirm the real
schema still has zero tables. Never expand runtime privileges to fix migration.

## 5. Transport enforcement: client gate before ON

| Client | Required acceptance |
| --- | --- |
| Health check | Prefer authenticated Unix-socket SELECT 1 using an existing protected option file, or verified TCP DNS:mysql. mysqladmin ping alone can succeed even when authentication fails. Inspect the actual command privately before changing it. |
| Root/bootstrap/admin | Unix-socket connections are permitted by secure transport; explicit plaintext TCP is not. Verify the actual fetch-db-secrets script and root paths without changing them. |
| Backups/restores/monitoring | Identify protocol, CA/hostname handling, users and extra backup privileges. Do not assume DML-only app credentials can perform the existing backup job. Prove a fresh backup and isolated restore with the proposed TLS/account settings. |
| App and Flyway | Existing separate credentials and PKCS12 VERIFY_IDENTITY. Test CA/DNS and isolated migration compatibility; live application startup remains disabled. |

If any client is unknown/incompatible, **keep enforcement OFF and block rollout**.
After client acceptance, in the existing admin session:

```sql
SET GLOBAL require_secure_transport=ON;
SHOW VARIABLES LIKE 'require_secure_transport';
```

Test new socket/verified TCP connections, health and backups; deliberately test
`--ssl-mode=DISABLED --protocol=TCP --host=mysql` with an existing reviewed client
and require a nonzero exit attributable to insecure transport. Never use real
credentials in argv. Make ON persistent by changing only that line in the approved
external server.cnf and re-running the owning-service restart acceptance under a
separate maintenance approval. Do not mix SET PERSIST with a file-only rollback
without reviewing/removing persisted overrides. Verify ON after restart; schedule
an owner reboot test proving original secret bootstrap, mounts, TLS and backups.

## Rollback / stop conditions

- Keep applications/delivery OFF throughout. If unhealthy after certificate switch,
  restore `compose.before.yml` to `/opt/goevent/compose.yml` and restart only the
  inspected owning service. Original autogenerated datadir certificates were never
  changed. Retain new certificate files for investigation; do not delete live mounts.
- If enforcement breaks a client, use the preserved admin **socket** connection to
  `SET GLOBAL require_secure_transport=OFF;` and restore the approved file setting
  before any restart. OFF does not undo an account's REQUIRE SSL.
- If reduction breaks a verified client, restore only the known original schema
  `GRANT ALL PRIVILEGES ON goevent_db.* TO 'goevent_app'@'%';` after approval.
  Restore its **recorded original** TLS requirement, not an assumed REQUIRE NONE.
  Lock the newly created migration account if abandoning the change; do not drop
  users/data automatically. Account/transport changes cannot be rolled back with SQL ROLLBACK.
- Approved rollback commands (only after checking the above conditions):

  ```sh
  # Certificate/config rollback; uses the preserved private original.
  sudo install -o root -g root -m 0600 /root/goevent-mysql-review/compose.before.yml /opt/goevent/compose.yml
  sudo systemctl restart goevent.service
  sudo systemctl is-active goevent.service
  sudo docker inspect "$MYSQL_CONTAINER" --format '{{.State.Health.Status}}'
  ```

  With a working root socket, transport/runtime-grant recovery is separately approved:

  ```sql
  SET GLOBAL require_secure_transport=OFF;
  GRANT ALL PRIVILEGES ON `goevent_db`.* TO 'goevent_app'@'%';
  -- Restore REQUIRE NONE only if baseline ssl_type was empty; otherwise its recorded policy.
  -- Lock goevent_migration at its actual approved host selector if abandoning the change.
  ```

- Restoring the old SAN-less certificate means VERIFY_IDENTITY remains blocked;
  do not bypass verification or start applications to make rollback appear healthy.
- For corruption/data loss use the proven isolated restore procedure under separate
  recovery approval. Never restore over a healthy filesystem as routine TLS rollback.
