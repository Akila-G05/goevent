# Application compatibility and deployment blockers

These are read-only findings from the current checkout, not fixes to application
files. Passing a packaging check does not make these images ready for deployment.

| Area | Observed behavior | Required resolution before production |
| --- | --- | --- |
| Backend packaging | POM has WAR packaging and no Boot plugin declaration. | Docker build invokes Boot 3.5.7 `repackage` after `package`; manifest must confirm `WarLauncher` and `com.goevent.GoeventApplication`. No external servlet container is introduced. Re-review if owners change artifact names or packaging. |
| Gateway packaging | Existing Boot plugin, Java 21, Boot 3.5.7, Spring Cloud 2025.0.3. | Package executable JAR and verify launcher. Packaging alone does not verify the Spring Cloud runtime compatibility check or service readiness. No version changes are made here. |
| Compiler target | Both POMs declare source/target 21, but the inherited compiler release is 17. | Container Maven commands explicitly set `maven.compiler.release=21`; owners must reconcile builds outside Docker separately. POMs remain unchanged. |
| Backend database | Default `localhost:3306`, DB credentials from variables, local URL disables TLS. | Supply private MySQL service DNS, matching persisted credentials, explicit deployment JDBC security and certificate trust configuration. No production database is contacted. |
| Flyway | Runs at backend startup; V1 exists; automatic baseline/clean disabled. | Verify existing disk database/history and schema compatibility on a restored copy. Non-empty schemas without history need a separately authorized baseline, never automatic baseline or deletion. Retain migration checksum checks and immutable SQL. |
| Flyway permissions/rollout | Startup migration uses datasource credentials unless a separate connection is supplied. | Approve a single migration owner, backup/restore and migration account privileges. Either supply a restricted separate migration account or approve a predeployment migration step and a backend runtime migration policy. Do not simply disable Flyway and leave an unmigrated schema. |
| MySQL DDL | Existing migration documentation notes nontransactional DDL and a Flyway 11.7.2/MySQL 8.4 support warning. | Verify vendor support and recovery from partial DDL before release; no dependency upgrades or automatic repair here. Existing money/schema issues are outside this infrastructure task. |
| Gateway routes | Four route URIs point at `http://localhost:8081`. Paths are `/goevent/api/...`. | Supply a reviewed external route configuration pointing every applicable URI at `http://backend:8081`. Confirm list binding, route order and end-to-end paths; do not rely on host networking. |
| Redis | Gateway uses reactive Redis rate limiting and response caching; default is `localhost:6379`. No Redis service exists in root Compose. | Approve Redis service/version/digest, private DNS, credentials/ACLs/TLS, capacity, eviction, persistence policy and health dependency. Test both rate-limiter and cache behavior during outage/recovery, not just TCP reachability. |
| Gateway cache | Broad API route includes response caching; requests with Authorization/Cookie bypass cache. | Owners must approve caching scope, privacy, invalidation, response-size limits and error/fallback behavior before exposing real authenticated/booking APIs. Infrastructure cannot prove all public GET responses are safe to cache. |
| Forwarded client identity | Rate limiter resolves the remote socket address. | Behind Caddy this may be the proxy address, sharing rate limits across clients. Owners must review trusted proxy handling and spoofing prevention; do not trust arbitrary client `X-Forwarded-For`. |
| Gateway management | Actuator health and gateway endpoints are exposed; gateway endpoint access is unrestricted in application config. | Limit management exposure through reviewed runtime settings and network boundaries; Caddy must not route `/actuator`. Verify actual management behavior before public ingress. |
| Vercel/API routing | Axios/Next defaults use `/api/v1`; VM gateway/backend expect `/goevent/api`. | Confirm the public API contract. A reviewed Vercel environment can set an absolute `NEXT_PUBLIC_API_BASE_URL` matching the gateway prefix, or owners can agree proxy/rewrite behavior. Existing Next rewrite preserves `/api/v1`; changing only its `BACKEND_URL` does not fix the prefix. Public frontend variables must never contain secrets. |
| Browser origins | Backend CORS bean lists localhost origins; no production Vercel origin is configured. Registration/effectiveness must be tested. | Owners must confirm how CORS is installed, allowed preview/production origins, credentials/cookies/CSRF and proxy behavior. A `CORS_ALLOWED_ORIGINS` variable alone is not evidence the current Java bean consumes it. |
| Authorization | Backend POM does not currently declare Spring Security. | Caddy/TLS/rate limiting do not replace server-side role/ownership controls. Owners must review access protection before public production deployment. No application security implementation is changed here. |
| Logging/filesystem | Apps write relative `logs/` files; runtime is non-root. | Provide approved writable log storage/rotation or reviewed logging overrides, a bounded temp filesystem, and no secrets/PII in logs. Set production logging levels externally. |
| Readiness | Gateway has Actuator with a Redis dependency; backend does not have Actuator. | Approve actual readiness/startup probes and HTTP checks. Do not advertise `/actuator/health` as an existing backend endpoint or treat image build/`java -version` as readiness. |
| Storage/DR | Root Compose defines a local named MySQL volume; Azure disk/backup/DR policies are not represented in checkout. | Verify existing protected disk mapping, fail-closed mount preflight and encrypted backup/restore evidence out of band. Preserve them; never provision a replacement or infer production paths from local Compose. |
| Release control | Current workflows only run backend/frontend checks; no ACR/OIDC/deployment approval definitions are present. | Authorized owners must provide reviewed scan gates, OIDC trust, protected environments, signature policy, digest manifest and VM pull approval transport in later work. Dedicated workflows are now prepared under the subsequent master directive; GitHub/Azure activation and required protections still need owner configuration. |

The Azure/Vercel/ACR/Key Vault/Caddy/pull-based design in `infra/README.md` follows
the task's deployment requirements. The checked-in ADRs describe the application
architecture; they do not establish that Azure resources or DR safeguards have
been configured or tested. Actual resource identities, domains and approved
operating procedures remain operator-supplied prerequisites.
